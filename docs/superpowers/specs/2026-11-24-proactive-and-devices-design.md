# Дизайн: проактивные решения и устройства домашней сети

Дата: 24.11.2026. Статус: согласовано пользователем кнопкой «Да, делай» в Telegram. Размер: проект.

## Намерение и причина

Пользователь не должен заходить в бот и набирать `/start`, `/status`, чтобы узнать, что агент
завершил работу или ждёт решения. Агент сам присылает итог и вопрос с вариантами ответа.
Второй режим: по запросу бот показывает все устройства домашней сети, подписывает известные
IP/имена, а неизвестные отдельно называет и спрашивает пользователя.

## Цели

- Один вызов для агента: «сделано + вопрос с вариантами» → сообщение и кнопки в Telegram.
- Постоянные кнопки в чате: «Устройства», «Что дальше», «Статус», «Помощь» — без набора команд.
- `/devices`: список устройств сети с IP, MAC (если известен), понятным именем и источником знания.
- Неизвестные устройства не выдумываются: помечаются «неизвестно» и предлагается подписка имен.
- Подписи хранятся локально и переживают перезапуск.

## Не-цели

- Управление роутером, изменение DHCP, блокировка устройств, доступ к админке роутера.
- Установка служб Windows и автозапуск.
- Любые изменения в APK дневника калорий.
- Сканирование за пределами настроенной подсети.

## Анти-цели

- Агент пишет «Дальше» в чат и ждёт, не отправив уведомление в бот.
- Пользователь нажал кнопку, агент не прочитал `/answers` и переспросил.
- Выдуманное имя устройства выдаётся за известный факт.

## Подходы

1. **Расширить текущий HomeBot (выбран).** Новые маршруты и команды внутри существующего
   процесса: `/handoff`, `/devices`, reply-клавиатура, локальный сканер. Плюсы: один процесс,
   один порт, уже есть transport/store/tests. Минусы: чуть больше кода в одном проекте.
2. **Отдельный сетевой сервис.** Сканер в отдельном процессе с своим HTTP. Отвергнут: два
   процесса, два порта, сложнее откат и диагностика ради одной функции.
3. **Чтение админки роутера.** Отвергнут: требует пароль, меняет поверхность атаки и часто
   недоступно; задание — только наблюдение сети.

## Решение по архитектуре

- `homebot/network.py` — `scan_network(subnet: str, arp_provider, resolver) -> list[Device]`:
  читает таблицу ARP (`arp -a`) через подменяемый провайдер, дополняет `socket.gethostbyaddr`,
  возвращает `Device(ip, mac, hostname, alive)`. Только чтение.
- `homebot/devices.py` — `DeviceRegistry(state_dir)` с файлом `state/devices.json`:
  `known(ip_or_mac) -> DeviceInfo | None`, `remember(ip, mac, label, source)`, `unknowns(devices)`.
- `homebot/bridge.py` — новые маршруты:
  - `POST /handoff` → `{"text": "...", "options": [...], "task_id": "..."}`; внутри вызывает
    `service.notify(kind="waiting")` и `service.ask(...)`, возвращает `ask_id`.
  - `GET /devices` → список из registry, помечает известные и неизвестные.
- `homebot/service.py` — `handle_command` расширен:
  - `/devices` — отправляет список известных и отдельно неизвестных; для неизвестных — `/ask` с вариантами
    «Подписать сейчас», «Пока нет», «Показать MAC».
  - все ответы команд несут `reply_markup` с постоянными кнопками.
  - `/info` — список команд и что они делают (BL-130, ранее отложен).
  - `/nextdown` — показать последний вопрос агента, который ждёт ответа.
- `homebot/telegram.py` — `build_main_keyboard()` (ReplyKeyboardMarkup, один ряд, resize=True);
  `setMyCommands` при старте при включённой отправке (без падения при ошибке).
- Известные устройства из текущих фактов: шлюз `192.168.1.1` — роутер; `192.168.1.2` — телевизор
  Xiaomi MiTV-MOOQ1; `192.168.1.13` — этот ПК (подлежит подтверждению). Всё остальное — неизвестно
  до ответа пользователя; источник поля `source` = `config`/`user`/`discovered`.

## Ограничения

- Только Python 3.13 stdlib, только Windows, только loopback bridge.
- Сканер не делает SYN-flood: не более 254 адресов, таймаут 0.2 с, без параллельных тысяч потоков.
- Тесты не обращаются к сети: ARP и resolver подменяются; transport — Fake.
- Секреты не выводятся в логи и ответы.
- Любому вопросу пользователя предшествует `/notify` с итогом; перед новым вопросом агент читает `/answers`.

## Решения автора после проверки дизайна

1. Свободный текст имени: добавляется команда `/label <ip> <имя>`. Кнопка «Подписать сейчас»
   присылает подсказку с примером; бот разбирает команду и сохраняет подпись. Отдельный режим
   ожидания текста не нужен.
2. Ключ устройства — MAC-адрес, IP как резерв. При смене IP подпись «переезжает» по MAC;
   `devices.json` хранит оба значения и источник.
3. `/handoff` принимает поля `summary`, `question`, `options`, `task_id`. Пользователь видит два
   сообщения: итог с припиской «Жду решения» и отдельный вопрос с кнопками.
4. `ask_id = "handoff:" + task_id`. Повторный вызов с активным тем же id возвращает тот же ask_id
   без второго вопроса.
5. `PendingAsk` получает поле `source` (`agent`/`device`). `/nextdown` ищет последний активный
   вопрос с `source=agent`, показывает его текст и заново выставляет кнопки из сохранённых
   параметров; вопросы устройств не подменяются.
6. В `Config` добавляется `NETWORK_SUBNET` (по умолчанию `192.168.1.0/24`). Сканирование живого
   адреса выполняется по `/devices`, результат кэшируется 30 секунд; фонового сканирования нет.
7. Приоритет подписей: пользователь > конфиг. Конфиг заполняет только отсутствующие записи и не
   перезаписывает пользовательские. `192.168.1.13` помечается как «не подтверждено пользователем»
   до явного ответа.
