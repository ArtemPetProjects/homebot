# Дизайн: единый home bot (BL-098)

Дата: 24.11.2026. Статус: **ожидает согласования пользователем**. Место: `E:\Projects\HomeBot` (новый проект, отдельный репозиторий).

## Намерение и причина

Пользователь просит одного общего бота вместо набора отдельных ботов под каждую задачу (BL-063, BL-064 объединены в BL-098). Первичная цель — **уведомления от агента**: что начато, что готово, что ждёт ответа пользователя. Во вторую очередь — команды и данные о домашней сети (понятные имена устройств, IP, уведомления о подключении). Бот не часть APK дневника калорий: это отдельная небольшая локальная программа на Windows.

Причина: у пользователя уже есть токен Telegram-бота и ID чата, и он подтвердил канал (Telegram) и способ связи (локальный HTTP-bridge).

## Цели

- Один процесс на Windows принимает события от агента через локальный HTTP и доставляет их в Telegram.
- Запросы подтверждения с вариантами ответа: inline-кнопки, ответ возвращается агенту.
- Работа без реальной отправки (`dry-run`) по умолчанию, пока пользователь явно не разрешит внешние эффекты.
- Никаких секретов в чате, репозитории и логах.
- Тестируемо без сети: подмена транспорта Telegram в тестах.

## Не-цели (в этой версии)

- Сканирование домашней сети, список устройств, понятные имена и уведомления о подключении — команды BL-063 отложены; в дизайне есть точка расширения, код не пишется.
- Изменения APK дневника калорий, телефона и телевизора.
- Установка автозапуска/службы Windows — запуск вручную; автозапуск отдельное решение позже.
- Облачное хранилище, веб-интерфейс, удалённое управление ПК.

## Анти-цели (что считать провалом)

- Утечка токена или ID чата в лог, чат, репозиторий или вывод команды.
- Отправка сообщения не в тот чат или от имени не того бота.
- Зависание агента в ожидании ответа, на который пользователь не нажал (нужен TTL).
- Дублирование уведомлений после перезапуска процесса.

## Подходы (рассмотрены до написания дизайна)

1. **Локальный HTTP-bridge (выбран).** Процесс слушает `127.0.0.1`, агент присылает JSON событий, процесс отправляет их в Telegram и принимает команды/нажатия кнопок через `getUpdates`. Плюсы: одна точка входа и для уведомлений, и для подтверждений с вариантами ответа; легко тестировать подменой транспорта; простой контракт для агента. Минусы: нужно держать процесс и порт запущенными.
2. **Файловая очередь JSONL.** Агент дописывает события в файл, процесс читает новые строки. Плюсы: нет порта, события не теряются при перезапуске. Минусы: возврат ответов и кнопок confirmation через второй файл неудобен, хуже для диалога BL-064.
3. **Разовый скрипт на каждое событие.** Плюсы: минимум кода, ничего не висит. Минусы: нет приёма команд и нажатий кнопок вообще, поэтому BL-064 не реализуется.

Выбран вариант 1: только он нормально закрывает запросы подтверждения с вариантами ответа, которые нужны агенту. Варианты 2 и 3 остаются запасными и не противоречат выбранному — при необходимости bridge может читать и файловую очередь как дополнительный источник.

## Контракт (как это будет работать)

### Конфигурация `.env` (в `.env.example` — только ключи с пустыми значениями)

```
TELEGRAM_BOT_TOKEN=
TELEGRAM_CHAT_ID=
LOCAL_API_KEY=
LOCAL_HOST=127.0.0.1
LOCAL_PORT=8765
SEND_ENABLED=0
POLL_INTERVAL_SECONDS=1
ASK_TTL_MINUTES=30
```

`LOCAL_API_KEY` — случайная строка, генерируется один раз при создании `.env`; все локальные запросы обязаны передавать заголовок `X-HomeBot-Key`. Токен и ключ никогда не выводятся в логи и ответы; при логировании запросов значения маскируются.

### HTTP-интерфейс (только loopback)

- `GET /health` → `{"ok": true, "send_enabled": false, "pending_asks": 0}`. Требует ключ.
- `POST /notify` → тело `{"kind": "started|done|waiting|info", "text": "...", "task_id": "..."}`. Ответ `{"ok": true, "queued": 1}`. В `dry-run` сообщение пишется в `state/outbox-dryrun.jsonl` и локальный лог, в Telegram не уходит.
- `POST /ask` → тело `{"id": "...", "text": "...", "options": ["Да", "Нет"]}` (2–8 вариантов). Ответ `{"ok": true}`; сохраняется в `state/pending.json`; в Telegram отправляется сообщение с inline-кнопками.
- `GET /answers?since=<n>` → `{"answers": [{"id": "...", "option": "Да", "seq": 12, "ts": "..."}]}`. Агент опрашивает это, чтобы получить выбор пользователя. `seq` монотонный, ответы не дублируются.
- `POST /ask` с истёкшим TTL или повторным `id` отклоняется.

### Обработка Telegram

- `getUpdates` long polling в отдельном потоке; Updates принимаются **только** от `TELEGRAM_CHAT_ID`, остальные игнорируются.
- Команды первой версии: `/start`, `/help`, `/status` (количество ожидающих запросов и состояние `send_enabled`), `/ping` (проверка, что бот отвечает локально, без сетевого запроса к Telegram).
- Нажатие inline-кнопки: `answerCallbackQuery` (убрать «часики»), `editMessageReplyMarkup` убрать кнопки, записать ответ в `state/answers.jsonl`, пометить запрос выполненным в `state/pending.json`.
- При `SEND_ENABLED=0` ни `getUpdates`, ни какие-либо методы Telegram не вызываются — опрос не запускается.

### Надёжность

- `state/pending.json` и `state/answers.jsonl` — локальные файлы, переживают перезапуск.
- Порядковый номер `seq` для ответов, дедупликация по `callback_query_id`.
- TTL запросов: при истечении запрос помечается просроченным, в `/status` видно количество просроченных.
- Ошибки Telegram (сетка, 429) логируются без токена; отправка повторяется ограниченное число раз с задержкой; при отказе событие остаётся в локальном outbox.

## Уточнения после проверки дизайна (мои решения)

Проверяющий задал 6 вопросов про крайние случаи. Ни один не меняет продукт для пользователя, поэтому решения приняты реализатором и помечены здесь; пользователь может их поправить при согласовании дизайна.

1. **TTL и ожидание агента.** При истечении TTL в `state/answers.jsonl` пишется запись `{"id": "...", "option": "__timeout__", "seq": N, "ts": "...", "reason": "ttl"}`. Агент, опрашивающий `/answers?since=`, получает завершение и не висит — это прямо закрывает анти-цель. В `/status` показан счётчик просроченных.
2. **`/ask` в dry-run.** Запрос принимается, сохраняется в `state/pending.json` и пишется в `state/outbox-dryrun.jsonl` с пометкой `delivered: false`; сразу создаётся ответ `option: "__undelivered__"` с seq, чтобы агент не ждал нажатия, которого в dry-run не может быть. Возврат `{"ok": true, "delivered": false}`. Inline-кнопки отправляются только при `SEND_ENABLED=1`.
3. **Outbox и дедупликация.** `state/outbox-dryrun.jsonl` — только журнал «что было бы отправлено», после включения реальной отправки не пересылается. `state/outbox.jsonl` — недоставленные реальные события с полями `event_id` (uuid4), `delivered_at`; при старте повторяются только записи без `delivered_at`, с ограниченным числом попыток. Дедупликация: `task_id` для `/notify`, `id` для `/ask`; дополнительный уникальный `event_id`.
4. **`callback_data` и лимит 64 байта.** В кнопку кладётся короткий токен `a:<token>:<idx>`, где `token` — первые 8 символов SHA-256 от `id`, `idx` — индекс варианта. Соответствие хранится в `state/callback_registry.json` и переживает перезапуск. Кириллический текст варианта в `callback_data` не кладётся.
5. **Время «занятости» `id`.** Идентификатор занят, пока запрос активен (не отвечен и не истёк). После ответа или TTL его можно использовать повторно; вечно растущего списка использованных id нет.
6. **Нажатие после TTL.** При истечении бот best-effort редактирует сообщение и убирает кнопки; поздний callback получает `answerCallbackQuery` с текстом «запрос истёк» и в `state/answers.jsonl` не пишется.

## Глубокий анализ (вторая проверка, исправления приняты)

Дополнительный разбор выявил пробелы, которые в первой версии дизайна привели бы к дублям, утечке токена или зависанию. Решения внесены сюда и считаются обязательными.

**Сеть и Telegram**
- `getUpdates` обязан сохранять `offset` в `state/telegram_offset.json`; без этого после перезапуска старые нажатия обработаются повторно. Long polling с `timeout=10`, сетевые таймауты: connect 5 с, read 15 с.
- Текст сообщения ограничен 4096 символами Telegram: обрезать с пометкой «… (обрезано)». `parse_mode` не использовать — произвольный текст события не должен ломать разметку.
- `429` обрабатывать по `parameters.retry_after`, сетевые ошибки — ограниченным backoff; при отказе событие остаётся в `state/outbox.jsonl`.
- `answerCallbackQuery` вызывать для **каждого** callback (иначе в клиенте останется «часики»); при истёкшем запросе — с текстом «запрос истёк».
- `editMessageReplyMarkup` требует сохранённые `chat_id` и `message_id` в записи запроса — добавить в схему `pending.json`.
- Никогда не логировать полный URL запроса (в нём токен): в логах только имя метода Bot API.

**Безопасность**
- Сравнение `X-HomeBot-Key` через `hmac.compare_digest`; конфиг проверяет, что `LOCAL_HOST` равен `127.0.0.1` или `localhost`.
- Ограничить тело запроса 64 КБ и требовать `Content-Type: application/json`.
- Игнорировать updates и callback'и не из `TELEGRAM_CHAT_ID`.

**Состояние и надёжность**
- Токен кнопки должен включать nonce времени создания: `token = sha256(id + "|" + created_at)[:8]`. Иначе старый callback после переиспользования `id` привяжется к новому запросу.
- `seq` ответов восстанавливать из `state/answers.jsonl` при старте; запись в файлы — атомарная (временный файл + `os.replace`).
- Один `threading.RLock` на общее состояние HTTP-потоков и потока опроса; корректный выход по `SIGINT`/`SIGTERM` с join потоков.
- `/status` отдаёт счётчики pending/answered/expired; `/health` — только флаги и счётчики, без значений конфигурации.

**Тестируемость и объём**
- Транспорт Telegram — внешний интерфейс с подменной реализацией в тестах; время передаётся как callable, чтобы тестировать TTL без ожидания.
- Тесты HTTP поднимают сервер на loopback в потоке и ходят через `urllib`; ни одного реального сетевого вызова.
- Первая версия сознательно ограничена: `/start`, `/help`, `/status`, `/ping`; никакого сканирования сети, автозапуска и служб Windows.
